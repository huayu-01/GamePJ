# 全程序化动画：按新资产前提修订选型与性能评估

日期：2026-10-30。用户补充：现有模型和动画基本不能作为动作参考，后续会替换；希望完整动作由程序生成，且部分敌人非人形。本说明据此取代原研究报告中“保留既有动作片段、主要加后处理”的默认选型。原报告的工程链路、API及资产现状调查仍可参考，但旧资产不再是新系统的制作起点。

## 结论

**可以以全程序化为主；约50名敌人的目标规模，不构成否决这个方向的理由。建议选择按身体结构分类的确定性动作生成，而不是让所有单位进行全身刚体物理模拟。** 目前没有新系统实测数据，不能承诺完整方案增加多少毫秒、或稳定达到多少FPS。

全程序化也不等于没有动作设计：蓄势姿态、发力方向、挥动曲线、步幅、节奏、支撑脚和恢复都需要设计，只是保存成参数、目标姿态和函数，不依赖外部动画片段。用少量人工设计的目标姿态经程序插值，仍属于这条路线；如果要求连这些动作约束也完全自动生成，问题就接近运动规划或学习控制，制作和运行成本都会上升。

非人形不天然更贵。只有身体、菌柄和帽子的敌人，弯曲／收缩／转头可以比人形动作简单；六足、多节身体、长触手且要求每个接触点准确的敌人，成本才会随接触点、链长与求解次数增加。应按身体结构及动作需求预算，不按“人形／非人形”二分。

## 1. 建议的完整系统

共享层负责程序动作时间轴、阶段、取消、目标快照、事件、姿态合成和重要程度调度；每种身体结构提供自己的动作生成器：

| 身体结构示例 | 动作生成方式 | 新模型主要适配数据 |
|---|---|---|
| 双足／岩块四肢 | 躯干与手臂姿态函数，脚步周期和落点，必要的手／脚IK | 躯干、四肢语义链，肢长、关节轴、pole、足底与握点 |
| 蘑菇／软体／植物 | 身体弯曲、伸缩、帽部延迟、蓄势与释放曲线 | 身体轴、根与末端、变形幅度，必要的变形骨或网格约定 |
| 悬浮／无腿 | 身体偏转、悬浮、后坐、朝向与释放末端曲线 | 悬浮中心、身体轴、攻击锚点；不需要为不存在的脚做落地IK |
| 多足／多节 | 分组步态、落脚规划、各腿短链IK；多节按曲线分布 | 每条腿或链的映射、支撑组、末端与碰撞探测规则 |

这些是结构例子，不替用户决定敌人造型。共用框架不意味着一个算法自动适配所有身体；以后换模型仍要校语义、比例和限制，但无需重做全部逐帧片段。

Godot4.7的SkeletonModifier3D可由C#实现骨姿态生成，没有AnimationMixer时也不要求先播放动画；有Mixer时则在它之后执行。双骨IK已有原生解析求解器，可用于短链，不必每条腿都使用多轮迭代算法。[SkeletonModifier3D](https://docs.godotengine.org/en/4.7/classes/class_skeletonmodifier3d.html)、[TwoBoneIK3D](https://docs.godotengine.org/en/4.7/classes/class_twoboneik3d.html)，访问于2026-10-30；本机4.7.2的C#绑定已在原报告核实。

## 2. 性能消耗拆解

以下高低为相对工程判断，**不是毫秒基准**。

| 模块 | 主要成本 | 相对压力／控制方式 |
|---|---|---|
| 程序动作阶段、事件表、曲线 | 标量运算、少量查表 | 通常较低；预编译曲线／事件数据，不每帧解析资源 |
| 躯干／头／武器／四肢目标姿态 | 向量、四元数与骨姿态写入 | 低～中；按实际骨数增长，注意C#与引擎调用次数 |
| 解析手脚IK | 每条短链目标计算与骨旋转 | 中；限制链数，缓存映射和肢长 |
| 地形探测与落脚规划 | 物理射线／形状查询、候选点选择 | 容易增长；探测和重新规划无需对所有单位每帧全量执行 |
| 长链／触手迭代IK | 关节数×迭代次数×活动链数 | 中～高；固定最大次数、误差阈值和活动数量 |
| 全身物理／主动布娃娃 | 刚体、关节、碰撞接触及控制 | 高且负载受场景影响；不作为50名单位的默认动作底座 |
| 蒙皮、网格、材质、阴影 | GPU及绘制提交 | 换成程序动作不会自动消失；同一模型同一骨数下，主要仍是相近的蒙皮／绘制工作 |

相对播放片段，程序方案省掉或减少的是动画数据、部分采样／混合工作，增加的是动作生成、求解、查询和脚本调度。究竟更快还是更慢取决于这两边；不能笼统宣称程序化必然更省CPU。Godot也明确每根需要模拟的物理骨都有成本，应删去不重要的物理骨。[官方布娃娃文档](https://docs.godotengine.org/en/4.7/tutorials/physics/ragdoll_system.html)，访问于2026-10-30。

## 3. 50名敌人的数量级

采用60Hz更新时：

- 50只、每只20根活动骨：每次更新1000根骨，约60000次骨姿态写入／秒。再读姿态、查父骨和设置目标会产生更多引擎调用；数字本身不能转换成耗时。
- 双足每足一条地面射线、全员每步都查询：50×2×60＝6000次射线／秒。若六足且其他条件相同，则为18000次／秒。增加脚趾采样、避障和落点候选会继续增长。
- 每只20根物理骨、50只全身模拟，会增加约1000根物理骨及其关节／碰撞工作；这与“计算1000根骨的旋转”不是同一种成本。

应限制的重点是无必要的全量查询、长链迭代和物理接触，而非先排除所有程序动作。一个无腿蘑菇可能只需要几根骨的函数计算；远处多足怪也可以采用简化落脚，不必每个脚趾独立探测。

建议先以“玩家＋50名敌人，完整程序动作系统新增CPU平均耗时不超过1～2ms”为**实验预算**。60FPS一帧约16.67ms，1／2／4ms分别相当于这份帧预算的6%／12%／24%。这些比例是算术，不是实际帧率损失；CPU／GPU并行和当前瓶颈会影响整帧结果。达到预算也不能保证整场战斗60FPS，更不能只看平均而忽略p99长帧。

原项目旧骨架待机测试只有469骨／100个播放器，不能拿来证明未来1000～2000根骨、多个动作生成器、IK和地面查询的成本。本说明不沿用该数据作新方案的性能预测。

## 4. C#、GC与节点控制

1. 绑定时缓存骨索引、链关系、rest、肢长和武器语义点；逐帧使用数值结构／数组，不递归查节点，不按骨名查找，不用LINQ制造临时集合。
2. 以单位为计算入口，批量计算姿态；不为每个骨骼、每个摆动轴或每条曲线新增独立脚本Tick。使用原生IK节点时也要统计真实节点和调度成本。
3. 查询参数和结果能复用的部分复用；注意Godot查询返回包装器／集合仍可能分配，不能因自己没有new就宣称零GC。使用分配计数和原生内存／对象计数一起验证。
4. 减少C#↔引擎重复调用，避免每根骨多次读取全局姿态。先在自身缓存里算，再统一写入。是否需要进一步原生实现，要由剖析结果决定，不先安装GDExtension。
5. 将“视觉姿态评估”“地面探测”“落脚重新规划”分开调度。主要攻击者和玩家保持足够频率；远处对象可减少昂贵探测，再平滑目标。单纯把全身动画降到15Hz可能产生顿挫，不能当作免费优化。
6. 场外／低重要程度可以减少视觉计算，但攻击时间轴、取消、命中和身体物理照常推进。降级不能使敌人静止无预警地攻击。

## 5. 战斗链路要改哪里

全程序化使原报告“保持AnimationPlayer事件读取不动”的假设不再成立。当前UnitAnimator按CurrentAnimationPosition读取方法轨道；不再播放片段时，需要用**同一个程序动作时间轴**生成姿态、武器轨迹和ATK／Dodge／GuardOn等语义事件，替换这段读取适配。

保留Ability的动作许可、SkillPlaybackId／实例归属思想、取消、命中快照和Movement的物理权威。不能一边由程序动作算姿态，一边另起一个独立Windup计时器决定伤害；暂停、顿帧、变速和取消后会容易错位。位移仍经Movement和碰撞，程序姿态不能直接挪模型伪装成单位位移。

这是完整系统的核心集成工作，开发风险高于增加几根骨的计算；它的开销通常不是主要算力项，但语义必须有专项验证。可见武器轨迹与实际命中体如何对应，应在原型中明确；不能在切换动画来源时顺便扩大攻击范围或引入自动吸附。

## 6. 新的验证起点

应改用从零建立的中性测试骨架／几何体，覆盖双足、无腿身体、多足三类，不以当前人物或动作片段为质量参考。先生成待机、移动、转向、攻击、受击与死亡，再接同一个程序动作时间轴测试取消、变速与顿帧。

1. 在相同模型上依次测试静态姿态→纯程序姿态→IK→地面探测→完整动作，分离每一项增量；不能拿不同模型之间的帧率差当动画成本。
2. 数量1／10／50／100，各自测试默认玩家镜头、近景、全场可见、群体同时攻击和转向；50是目标条件，100是压力观察，不改生产人数。
3. 同机、同负载、固定输入与种子，重复OFF／ON对照，保留首次使用与暖场样本；记录平均／p95／p99整帧和CPU／GPU、托管分配、GC、活动骨链、物理查询与节点数。
4. 在生产战斗负载里再测，确认动画预算不会挤掉AI、弹道、导航和反馈。只在空场跑50个角色得到的结果不能直接作为实战上限。

Godot官方建议先用剖析定位真实瓶颈，且计时工具本身会影响运行；必要时检查原生CPU／GPU，而非只看C#脚本作用域。[CPU优化文档](https://docs.godotengine.org/en/4.7/tutorials/performance/cpu_optimization.html)，访问于2026-10-30。

本轮仍为研究修订，未创建测试骨架、修改生产代码或执行新动画基准。因此当前结论是“技术与预算上值得验证”，不是“50只完整程序动画已通过性能验收”。

## 7. 玩家动态混合、下落攻击与连续招式的覆盖范围

同日补充需求：猎手需要脚部持续移动、手部同时攻击的动态混合；武器大师需要下落攻击和连续招式。**这些功能可在前两类实现范围内完成：程序姿态／攻击曲线，加双足步态和有限手脚IK；不必因此采用全身物理、多足复杂规划或长链迭代。** 这是实现能力判断，动作质量和性能仍待原型。

| 需求 | 所需动作机制 | 与现有玩法边界 |
|---|---|---|
| 猎手边走边攻击 | 下半身按实际速度／方向生成步态；上半身按瞄准和攻击相位生成姿态；骨骼遮罩分配权重，腰／骨盆过渡协调；最终再做必要手脚IK | 只有技能规则允许移动时才移动，姿态层不能自行放开ActionMovement；侧移／后退也应生成正确落脚方向 |
| 武器大师下落攻击 | 空中准备→下冲→接触→恢复的全身程序动作；空中关闭地面锁脚，接触阶段读取真实碰撞／接地 | 真实位移归Movement；空中接触伤害与落地伤害各沿对应技能事实，不能把全部伤害都延到落地 |
| 武器大师连续招式 | 每段各有蓄势／有效攻击／恢复曲线及事件，下一段从当前姿态与运动趋势衔接，支持输入缓冲和取消 | 连招推进、窗口、出手和移动不得使用独立于程序动作的第二套计时；保持技能既有段号和播放代次归属 |

程序姿态混合可以直接对生成的局部骨位移／旋转加权，并用四元数插值处理旋转；不必先生成外部动画片段，也不强制AnimationTree。Godot的SkeletonModifier3D提供最终姿态写入入口，遮罩、动作优先级和相位过渡是项目需要实现的控制层。

上／下半身不能在腰部完全切断：攻击要有胸腰发力，移动又需要骨盆保持支撑，应给躯干分布权重。大幅近战、下落攻击可以临时提高全身动作权重；是否限制实际移动仍由技能规则决定。普通移动叠加攻击时，也不要把走路的摆臂完整加到持弓／投射动作上。

建议的求值顺序是“读取同一动作时间轴与真实Movement状态→生成步态和攻击姿态→按骨遮罩／优先级合成→手脚末端约束→输出一份骨架姿态”。只渲染一份角色，不复制两套角色或逐帧烘焙网格。相比单动作，会增加姿态生成和混合计算，但不意味着蒙皮与绘制成本翻倍。

下一轮原型应明确覆盖：猎手前进／后退／侧移同时瞄准、蓄力和出手；武器大师空中转入下落、提前撞到目标、真实接地恢复；至少三段连续招式及任意合法取消。记录腰部扭转、脚滑、武器握持、动作连续性，并验证事件、位移、伤害和取消都与同一个权威动作相位一致。只演示静止挥手或原地走路，不能作为上述需求的验收。
