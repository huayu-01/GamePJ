## 3. 敌敌无碰撞＋导航避让

### 可行，但不是零成本替换

推荐把它视为“改善拥挤与接近行为的候选”，性能收益由对照决定。取消敌敌实体接触可能减少接触处理；增加RVO会增加邻居查询、速度求解与同步开销，未必净提速。RVO负责局部选速度，导航网格仍负责绕地形找路，两者不能互相代替。

官方说明避让本身不知道导航网格和物理碰撞，极端正面对向等情况也可能失败，因此不能承诺无碰撞后永不重叠。[导航代理与避让](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationagents.html)、[NavigationAgent3D成本及参数](https://docs.godotengine.org/en/stable/classes/class_navigationagent3d.html)。

### 当前工程的接入边界

1. 身体碰撞层与阵营／攻击层分开配置。只取消敌敌身体阻挡；保留玩家—敌人、单位—地形、玩家攻击—敌人、敌人攻击—玩家和弹道地形规则。现有共享UnitBody层不能直接从所有单位Mask里删除，否则玩家冲撞和其他接触机制也会失效。
2. 保留现有UnitNavigation和地图路径查询，可用NavigationServer3D Agent RID接入避让，不必强行为每敌增加一个NavigationAgent3D节点。RID也有生命周期和同步成本，不等于不耗CPU。
3. 不同体型继续使用适合自己的路径地图，但地面避让需要共享模拟map，并正确设置半径、速度上限、邻居范围、优先级与层。不能把小怪、大怪分别隔离到互不相见的避让世界。未来飞行另定高度规则。
4. 避让只影响普通主动移动的XZ期望速度；重力、高度、击退、技能位移继续由CharacterMovement统一处理，不能用safe_velocity覆盖垂直分量或一律覆盖冲锋速度。
5. 同一玩家位置不能成为所有敌人最终停靠点。需要按近战距离、攻击占位、远程距离设计不同接近点；停止前摇的敌人也应成为其他人的避让对象。否则无实体碰撞时可能从“挤住”变成“叠在玩家身上”。
6. 生成、遁地、瞬移仍要选导航网格上的有效位置，并检查落点占用；局部避让不能修复出生时已经深度重叠的单位。

当前重叠现象还没有复现归因。下一步需区别模型外轮廓与胶囊尺寸、生成／瞬移位置、技能位移、正常多人拥挤，而不是先假定碰撞失效。

### 首领冲锋推开敌人

**可以独立保留，预计属于中等兼容工作，当前没有这一专用实现。** `ChargeAttackAbility` 用攻击盒处理敌对目标；`MoveAndSlide` 没有自动把角色碰撞转换为另一个角色的冲量。

可在首领冲锋期间按扫过体积查询同阵营小怪，排除自身、去重／限频后施加物理推力，保留地形处理，不经伤害、受击硬直或敌对攻击盒。体型、质量、不可移动单位及免控规则应明确，不能因为推力顺手破坏精英护甲或首领免控设计。

已有 `ApplyPhysicalImpulse` 接口，但 `CharacterMovement` 的速度覆盖分支忽略外力速度：小怪正在冲锋／扑击／后跳时，单纯调用加力不保证立即被推开。需要为这类位移明确叠加或抢占规则；不能把已有接口当成已经完成的兼容。

玩家“快乐奔跑”通过滑动碰撞识别目标，必须保留玩家—敌人的接触，或另行迁移检测；本方案优先保留，因此不需要改变其玩法。首领推开可做独立开关，是否保留不阻塞普通移动避让试验。

### 50敌人的回退

如果避让导致穿插、抖动、卡门、攻击密度失控或性能不理想，保留原碰撞，并独立评估约50敌人方案。强化个体需同时校准行为、压力预算、伤害窗口、血量、经验和升级速度，不能只翻倍血量把战斗拖长。

性能统计应包含首领、精英和召唤物的真实活跃数量；“50”的硬上限是否约束召唤应在落地前写清，不能悄悄改变“召唤免费且仅有限一批”的既定规则。最终若选择50，明确记录为设计目标调整，与100敌人的同条件性能结果分别报告。

## 4. 视锥剔除、遮挡剔除和Jolt

**自动视锥剔除已经由Godot执行。** 屏外物体通常免于主视图绘制，但这不会自动停止AI、物理、技能、计时或骨骼更新，也不能简单推定阴影等其他通道都没有成本。无需通过缩小相机FOV来“开启”它。[官方3D性能说明](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)。

可继续调查特效包围盒与过大的自定义AABB是否降低剔除机会，以及屏外纯表现是否适合暂停。不能以是否在镜头内直接冻结整只敌人：转镜头不应改变追击、远程攻击、持续效果、技能完成或死亡结算。

**遮挡剔除是另一项机制。** 适合有明显大墙、建筑和室内遮挡的关卡；开放死战场可能收益有限，还会增加CPU工作。先基于场景遮挡结构决定是否值得制作代理，不直接全场开。[官方遮挡剔除说明](https://docs.godotengine.org/en/stable/tutorials/3d/occlusion_culling.html)。

**Jolt已经启用。** 本轮不再列为“切换后可获得的收益”。后续要评估碰撞形状、接触密度、Area监测和MoveAndSlide，而非重复切换引擎。[Jolt官方说明](https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html)。

原GC统计只有次数和总分配，没有与长帧逐帧关联，现阶段无法证明GC是1%低帧主因；也不能把Physics监控毫秒与平均帧时简单相加。

## 6. 节点、骨骼、材质与RenderingServer

### 优先查实际工作，少按节点数量下结论

普通敌人22～31节点，计划行为类26节点，不像每敌数百节点的明显场景树膨胀。值得查的是空闲回调、常开Area、多个表面、动态材质和动画工作；空Node和活跃蒙皮Mesh不能按同等成本计算。

`AttackHitbox` 当前刻意常开Monitoring，以避免反复切监测后静止目标丢重叠；是否能优化要先做接触回归。不能只为节点／Area计数好看直接关闭。经验球已有MultiMesh；类似纯装饰、重复静态件、视觉残影和无独立交互的批量表现，可继续按实际数量评估合并。

### 骨骼／动画与逻辑必须分开

当前 `UnitAnimator` 自行读取动画播放位置并派发关键帧，事件包括攻击、动作和格挡窗口。屏外或远处直接停整个AnimationPlayer／粗降更新，会改变攻击时刻或遗漏事件。应先测原生骨骼、动画轨道、蒙皮、绘制提交的成本，再考虑视觉更新预算；逻辑事件计时保留准确性。

部分导入已开自动LOD，需确认实际模型是否产生有效层级、运行时切换和视觉是否合格；自动网格LOD不能代替骨骼／动画预算。材质侧优先检查重复资源、不同表面、临时材质实例、透明叠加和描边额外通道。相同材质并不保证所有蒙皮对象自动合成一次绘制；必须以draw calls和GPU采样判断。

模型尚未最终确定，本轮不修改骨架／模型源。后续先统一美术规格和接入契约，避免对暂用模型做难迁移的专门重写。保留既定护甲、预警、状态描边表现，不把直接删效果当作免费优化。

### RenderingServer的合适范围

Godot的Mesh等节点底层已经使用RenderingServer。直接操作RID主要省去大量对象的节点层管理，不能自动消除三角形、骨骼蒙皮、透明像素或碰撞成本。[官方Server使用说明](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)。

优先候选是大量、简单、仅表现的实例；能用MultiMesh解决时先衡量MultiMesh。带骨骼、技能事件、受击、状态和武器挂点的完整敌人不优先改成纯RID架构。直接管理需要负责释放RID、资源强引用、可见性及同步，维护成本明显上升，也不应混用节点与Server争夺同一对象状态。

## 7. 建议的决策与验证顺序

|阶段|建议|验收证据|
|---|---|---|
|A 分配与空闲更新|优先；每类单独实施和对照|分配调用栈、每帧分配、GC时刻与长帧关联；玩法、画面、AI决策频率保持一致|
|B 拥挤行为试验|独立可回退开关；先定位现有重叠，再比较碰撞和避让|相同人数、画质、敌人构成，观察窄口、停靠、前摇、冲锋、击退与帧时|
|C 骨骼／LOD／材质|先分离原生动画与渲染成本，再选具体手段|骨骼／动画开销、draw calls、GPU帧时；攻击／格挡事件及模型更换不受损|
|D 50敌人回退|仅在体验或成本不合适时选择|与100目标分开报告，检查压力、奖励、召唤与完整一局节奏|
|E Server与遮挡|有大量简单实例或有效遮挡证据后再做|有明确热点与收益才承担架构／场景维护成本|

碰撞试验至少区分：A原碰撞；B仅取消敌敌碰撞、不加避让；C取消敌敌碰撞＋避让；必要时D再加攻击接近点。50／100人数分别测试，不能把减少人数的收益归因给避让。记录平均／1%低帧、p95/p99帧时、物理与导航成本、实际存活数、持续重叠、卡门和攻击密度；补齐转镜头、场外远程、精英、首领、召唤及完整一局。
