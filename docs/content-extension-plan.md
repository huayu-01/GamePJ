# 内容扩展与解耦计划

2026-10-24用户确认实施，随后要求完成余下全部内容。目标是新增增幅、敌人、模型和脚本时减少需要同时理解、修改的模块。

## 当前范围（本计划已完成，2026-10-25）

本计划剩余实现、制作文档、公共验证和文件整理已经完成；验证覆盖与尚未定位的问题分别记录如下：

- **增幅与符文**：91项增幅、11枚符文均通过 `Effects` 安装。生产资源已移除旧 `ApplyHandler` 和 `HandlerParams`；注册表只编译效果与奖励元数据，旧格式在兼容层翻译。技能容量也有明确的 `AbilityChargesTuning`，不再用任意字符串属性覆盖生产技能。
- **特化**：23项全部使用各自强类型定义和普通C#行为实例。协调器只负责来源租约、固定次序与事件分发，标记、计时、伤害修正、技能订阅和区域归各行为持有。同类多来源不重复建行为，最后来源撤销时精确清理。
- **武器增强**：通用 `AbilityTuningRewardEffect` 与 `IAbilityRewardTuning` 管理参数来源，各技能自行消费增强；能力快照仅保存增强字段。撤销早期来源时还原基线并重放剩余来源，不重置动作、冷却或已经发射的攻击。
- **事务与清理**：组合先应用、再提交一次性收益；应用或提交失败均逆序回滚。加甲、血铠转换有明确失败收据；正常撤销不追缴一次性护甲。符文与持续规则同步退订，不靠节点名前缀清理。
- **交互与收益**：`InteractionDefinition` 分开引用后端和模型，16种内置资源复用旧Kind，自定义定义无需新增中央Kind。八行节点明确引用选择、资源、治疗或商店策略；独立会话管理单次完成、取消和购买退款。自定义节点行直接提供自己的价值标签、波数与压力配置。
- **验证与规模**：全部21类索引数组、特化总数及奖励分类数量集中在 `content_inventory.tres`。Main先核对实际数量再比较原8指标，保留原5类历史红标。公共验证设施管理构建、锁、进程、stderr与五份存档；历史入口保留各自场景／机制／截图断言，可能写盘的旧入口使用独立用户目录。错误专项名称在构建前拒绝。
- **制作和文件**：作者指南已按当前资源入口更新，原329份遗留根目录指纹JSON转入 `Logs/maintenance/root-fingerprints-20261024-remaining/`，内容与SHA256保全。新增报告、指纹和引擎日志继续进入 `Logs/`。

保留的边界是旧存档Id与枚举兼容、原技能槽／ATK快照／导航／移动所有权，以及另一会话维护的重击、重击Plus、蘑菇资产和专用接入。大多数候选模型和骨架仍可替换；本轮没有将其确认为最终稿。英文仍只有两个示例，未宣称完整多语言或性能提升。

当前制作方式见[作者指南](content-authoring.md)、[增幅](upgrades.md)与[符文](rune-system.md)。以下第一至第五阶段及末尾评估为迁移历史，其中“未迁”描述表示当时状态。

## 第四阶段：弹体与地面位移动作

- 六份生产计划的12个动作段迁入独立定义和执行器：五种发射方式、起跳、俯冲、遁地、两段后跳及两段配套近战。与前两阶段组合后，这十份计划的动作都通过定义接入；重击、重击Plus和蘑菇的模型及其专用接入保持原样。
- `EnemyProjectileMotion`统一前摇预览和实际发射的初值；旧Kind发射入口也复用同一实现，保留伤害乘区、航程、转向、重力、查询几何、碰撞半径和全局限速。`ProjectileScene`允许更换弹体外观场景，错误根类型在制作期报告；已发射弹体独立存活，预警随弹体清理。
- 俯冲执行器独立管理飞行与落地伤害窗口，真实碰地后才开命中体，落地后沿用原0.12秒窗口。协调器读取通用时长与预警接口，不再替新俯冲动作改写步骤Kind或临时重启计时。

## 启动时确认的增幅与本地化方向（历史）

- `RewardConfig`保留身份、抽取资格和效果列表；把各处理器专用参数逐步收进对应的强类型效果资源。
- 使用效果定义与独立运行实例：定义负责参数、引用、校验和创建；实例负责持有者、计数、冷却、订阅和撤销。共享资源不保存玩家或本局可变状态。
- 同类数值变化共用效果实现；复杂增幅组合已有触发、条件、施加效果和表现。独特武器行为保留专用能力组件，不为每个增幅名字建立一套子类。
- 注册表逐步缩减为兼容入口与工厂；允许预编译为委托执行，选择依据是可维护性和实测，不能宣称委托或继承天然最快。
- 玩家文本使用稳定`NameKey`／`DescriptionKey`，显示时取整句译文再填命名参数，切换语言刷新界面缓存。数值与实际效果共用来源；不靠拼接词片生成所有语法。
- `Id`、事件标识、属性键和存档键不翻译。当前`Requires="雷之印"`等中文逻辑token应兼容迁到`rune_lei_seal`等稳定Id，不能直接替换成其他语言的显示名。
- 应用与撤销按实例归属管理修饰器、事件、冷却和表现；换装、死亡、取消冒险、重开和移除效果必须成对清理。持续更新可以集中调度，纯数值不强制创建逐帧Node。

## 原迁移方法（历史）

1. 先补制作入口、模板和校验，给每一类内容明确必填项、消费者、样板和最小测试。入门流程见[新增内容](content-authoring.md)。
2. 建立增幅效果定义／实例与撤销句柄，迁一个纯数值和一个事件触发效果，保持旧`ApplyHandler`可读。
3. 文本键与稳定前置Id独立迁移；保持存档、旧Id和资格规则兼容。
4. 再按真实新增需求迁技能适配器、敌人步骤和表现档案；每次用已有内容证明等价后扩展。
5. 最后收敛流程编排与验证脚本公共设施。不要同时替换战斗结算、导航和整个技能系统。

保留已经有效的边界：当前技能槽唯一、`PlayerLoadout`统一换装、`AttackInstance`伤害快照、`MapManager`有效点、`CharacterMovement`移动所有权、事件归属与派生限制，以及UI顶层路由。新增框架应复用这些契约。

本轮没有性能基准证明某种面向对象形式更快。后续比较应固定相同构筑、敌人数和攻击频率，记录CPU耗时、分配、查询／订阅次数，避免为了类数量拆散已经清晰的责任。
