# 原始设计纠偏 J10：弓的蓄力档位（间隔 0.3s / 基础1+后置3=4档）· 弹速下调 · 快弹不漏怪

2026-10-17。用户原话：

> 「弓这里的倍率确实过高了，蓄力的档位有问题，这里的间隔应该是 0.3 我填成 0.1 了，另外是弹速过快导致能漏怪的，
> 考虑拉长碰撞体的同时，降低整体弹速，太快的弹速在每次发射前加入射线的检测；」
>
> 「同时，基础蓄力不要让后续蓄力也同时生效，比如这个弓的武技1，实际是 3 档，蓄力后才开始增长，其他武器的也是；」
>
> 「第一个 基础蓄力 + 3 个后置档 = 总共 4 个威力档」；「伤害的增长不是这么算，而是 30+30+30+30... 这么算」

本批拆成 4 个独立提交：**A** 档位 / **B** 弹速 / **C** 投射物扫掠（基础设施）/ **D** 把扫掠接到弓的表列并实测。

Main 自测退出码 0、stderr 0 字节、8 条硬指标逐字一致；四存档 SHA256 跑前＝跑后；`selftest.flag` 不存在。

## 病根

| # | 现象 | 真正的原因 |
|---|---|---|
| A | 「间隔应该是 0.3，我填成 0.1 了」 | 表行 `skl_a3_w1_1.ChargeStepSeconds = 0.1`（文档原意 0.3）→ 满蓄 5 个后置档 ×2.5 |
| B | 「弹速过快」 | `Speed = 220` + 每档 `30` → 满蓄 370 m/s，一物理帧飞 6.17m |
| C/D | 「弹速过快导致能漏怪」 | **不是碰撞体太短**：`Projectile` 根本没有 `CollisionShape3D`（弹道是射线）。真因是既有路径**每物理帧只做一次 `IntersectRay`（只返回最近的一个命中）**，穿透后直接把位置推到**帧末** —— 同一帧线段里后面的单位再也不会被检测到 |

## A：`ChargeStepSeconds 0.1 → 0.3`，`ChargeMaxSeconds 1.0 → 1.4`（基础 1 + 后置 3 = 4 个威力档）

`Ability.ChargeMaxStepsEffective` = `min(ChargeMaxSteps, floor((ChargeMaxSeconds − 基础) / step))`，
所以 "3 个后置档" 要求上限 = `0.5 + 3×0.3 = 1.4s`。原文那句「最多蓄力 1 秒」已按用户裁定改成 1.4 秒（表行 `Note` 写明来源）。

⚠️ **改的过程中发现一个真的浮点缺陷**：`(1.4 − 0.5) / 0.3` 在 float 下是 **2.9999998**，`Floor` 会得到 **2 档**，
"基础+后置3"直接变成 2 档。已在 `Ability.ChargeMaxStepsEffective` 里加 `+1e-4` 档容差
（只影响"表值正好落在整数档边界"的行；长枪 `(2.0−1.0)/0.25 = 4` 精确、短弩走 `ChargeMaxSteps` 封顶、
其余 `step ≤ 0` 直接返回 0 —— 既有行结果一个都没变，四条回归探针可证）。

### 威力阶梯（⭐ 公式是**加法**：`ChargePowerScale = 1 + (ChargeStepScale − 1) × 档数`）

| 档 | 蓄力时长 | `ChargeSteps` | 威力 | 单发伤害（表值 24 × 玩家倍率 1） | 弹速（B 之后） |
|---|---|---|---|---|---|
| 基础 | 0.5s | 0 | **×1.0** | 24 | 160 |
| 后置 1 | 0.8s | 1 | **×1.3** | 31.2 | 180 |
| 后置 2 | 1.1s | 2 | **×1.6** | 38.4 | 200 |
| 后置 3（满） | 1.4s | 3 | **×1.9** | 45.6 | 220 |

改前（`step=0.1 / maxSec=1.0`）= 5 个后置档：×1.0/1.3/1.6/1.9/2.2/**2.5**，满蓄伤害 60、弹速 370。
**这条 `×2.5` 正是用户上一轮裁定「弓五档 2.5 倍」的那个数** —— 说明"加法"口径与旧裁定一致；
现在变成 4 档 ×1.9（伤害 60 → 45.6、弹速 370 → 220），这就是用户说的"倍率确实过高了"的收敛。

## B：弹速 220 → 160，每档 30 → 20（⚠️ 预设值，等用户确认）

- 基础 160（原 220，低 27%）、每档 +20（原 +30）；满蓄 220（原 370）。
- 理由：① 一物理帧位移从 6.17m 降到 3.67m，"一帧跨过两只怪"的尺度显著缩小；② 满蓄弹速回到旧**基础**值，
  手感上仍是"蓄满更快"，但不至于快到看不清；③ 只动**弹速两列**，伤害/倍率/击退/CD 一个数字都没碰。
- 表行 `Note` 已把"J10 预设、等用户确认"写进去。

## C：`Projectile` 每帧"线段多命中"扫掠（`SweepMaxHits`，默认 0 = 逐位不变）

`Projectile` 里新增 `[Export] int SweepMaxHits`（默认 **0**）与 `SweepFrame(from, to)`：

| 约束 | 实现 |
|---|---|
| **碰撞体按速度动态变长** | 每物理帧的"命中体"就是 `from → to` 这条线段，长度 = `|velocity| × delta`，**每帧按当时的真实弹速重算** —— 不是静态加长（也没有 `CollisionShape3D` 可加长：既有弹道本来就只走射线） |
| **线段上的每个单位都结算** | 逐段重扫：拿最近的命中 → 结算 → 把它排进 `_excludedBodies`（与既有穿透排除同一套）→ 从命中点继续扫到帧末 |
| **不重复结算** | 打过的 body 进排除表 + `HitTracker` 策略双保险；探针断言"这一发里每个靶正好 1 次" |
| **撞到 World 停下** | 命中体不是敌对 `Unit` → 立即 `QueueFree()`，不穿地形 |
| **默认行为不变** | `SweepMaxHits ≤ 0` → `_PhysicsProcess` 直接走既有单次 `IntersectRay` + `ResolveImpact`，**一行都没改** |
| 预算 | `SweepMaxHits` = 一帧最多结算几个（循环保险丝）；真正的命中数另受穿透预算限制。预算用完就停在最后一个命中点，剩余线段留给下一帧，**不跳过** |

## D：接到弓的表列（`SweepMaxHits = 8`）＋ 贴脸双怪实测

- `ArrowVolleyAbility` 新增 `[Export] int SweepMaxHits`（默认 0），`FireProjectile` 原样传给投射物
  —— 强类型 `[Export]` 列 + 既有技能行 `Params` 通路，**没有 `Godot.Get/Set` 字符串反射**。
- **只有 `skl_a3_w1_1` 配了这一列**；短弩/灵剑/能量掌等行不配 → 走既有单路径。

### ⭐ "贴脸双怪"实测（探针真实按键 → 真实释放 ATK → 真实命中）

几何（探针把这两个数打出来）：蓄 2.05s 的大箭弹速 **260 m/s** → **单帧线段 4.333m**；
两靶 `z=17.6 / 16.0`（半径 0.5，跨 `z∈[15.5, 18.1]`）**都完整落在同一条线段里**（枪口 `z≈19.4` → 帧末 `z≈15.067`）。

| 对照 | 扫掠预算 | 命中 | 读数 |
|---|---|---|---|
| ⓐ **关掉扫掠**（= 改动前 / 任何没配这一列的武器） | 0 | **只中 T1** | T2 生命 100000/100000 一点没掉 |
| ⓑ **开扫掠**（表值 8） | 8 | **T1 → T2** | 伤害 60 / 120（第二下暴击），**同一物理帧 695 / 695** |
| ⓑ 不重复结算 | 8 | T1 1 次、T2 1 次 | 这一发正好 2 次命中 |
| ⓒ 墙夹在两只中间 | 8 | **只中 T1** | 墙后靶生命不变、箭撞墙后消失（场上投射物 0） |

"同一物理帧"这一条是关键：ⓐ 的漏怪不是"下一帧补打"，而是**永远打不到**（射线只向前走，
帧末位置已经越过那只怪）。ⓑ 把同一帧线段上的两只都在**这一帧**结算完。

## ⭐「基础蓄力期间不加档」的实测（用户追加要求）

代码上本来就是这么写的（`Ability.RecountChargeSteps`：`ChargeTime <= 基础` → 0 档；`ChargePowerScale` 随之 = 1），
本批**没有改这一块**，但按用户要求实测确认了：

| 读数 | 值 |
|---|---|
| 真实按住到 **0.352s**（< 基础 0.5s） | `ChargeSteps = 0`（期望 0） |
| 同上 | `ChargePowerScale = ×1.0`（期望 1） |
| 同上 | `ChargeProgress = 0.704`（还没蓄满） |
| 这一按松手（没蓄满） | `LastReleaseAborted = True`、场上新弹体 **0** 个（不释放） |
| 真实箭「刚过基础就松手」（松手快照 0.52s） | 伤害 **24**（= 表值 24 × 倍率 1，**不含任何档位加成**）、弹速 **160** |
| 真实箭「过了第 1 个后置档」（0.814s） | 伤害 **31.2**（×1.3）、弹速 **180**（+20） |

→ **基础蓄力那 0.5 秒里伤害完全不动，越过 0.5s 才开始按档增长**；用户担心的"基础蓄力让后续蓄力同时生效"
在弓武技1 上不成立，也没有任何子类自己乘了 `ChargeTime` 之类的东西（`FireVolley` 只读基类给的
`_releasedPower` / `_releasedSteps` 快照）。

## 边界 / 不确定处

1. **B 的弹速 160/20 是预设值**，等用户确认；只动了弹速两列。
2. **龙之箭口径**（甲/乙/丙）等裁定；本批没动它的表行。
3. **长枪武技2 是 5 档**（基础+后置 4，×1.8），与新口径"基础+3=4 档"差 1 档；**本批没改**，等确认。
4. `Ability.ChargeMaxStepsEffective` 的 `+1e-4` 容差是**共用基类**改动：只影响"表值正好落在整数档边界"的行，
   既有行（长枪 4 档精确、短弩用 `ChargeMaxSteps`、其余 `step ≤ 0`）结果全不变；四条回归探针可证。
5. **扫描只给弓武技1 配**（表列 `SweepMaxHits=8`）。其余武器仍每帧只结算最近 1 个命中（默认逐位不变）；
   将来要给别的武器也开，只在它自己的表行加同一列即可（不改 C#）。
6. `SweepMaxHits = 8` 是"一帧最多结算几个"的保险丝；真实命中数另受穿透预算限制
   （`_pierceLeft = Pierce + attack.Pierce` 这个**既有**双算没改，大箭实际预算 198）。
7. **0.6m 枪口盲区**是既有行为：箭在角色前方 0.6m 出生，贴着角色的目标本来就不在首帧线段内（本批没改）。
8. ⚠️ "拉长碰撞体"这条的真相：`Projectile` **没有碰撞体**（既有弹道只靠射线），所以"长度"一直就是
   `弹速 × 物理帧时长`；漏怪不是长度不够而是**每帧只取一个命中**。本批把"命中体 = 整条本帧线段"
   （长度逐帧按弹速重算）＋"线段上全部结算"一起落地 —— C 与 D 是同一处修复的两面。
   如果用户要的是**加粗**（射线有半径、能打到脚边擦过的怪），那是另一件事：要做 `IntersectShape`
   （球形/胶囊扫掠），本批没有做（`IntersectShape` 不返回命中点，会改变命中特效位置）。
9. 本批**没有截图**（证据是文本读数 + 存档哈希）；真机手感（160/20 是否合适）留给人手 MCP 复核。
10. `Scripts/Testing/BowSweepProbe.cs.uid` 是编辑器生成的，与工作区里其它未跟踪 `.uid` 同批，不入库
    （`_BowSweepProbe.tscn` 引的是 `.cs` 路径）。
